# The API keys

Why a key is shown once, why revoking is not deleting, and why the three keys a box holds are
three different things and never substitute for one another.

Written 2026-09-07, after a gateway stood up in the box's exact posture — Postgres, an ops key, no
development key — answered `401` on `GET /v1/routes` to every worker and every app, because
`migrations/0002_api_keys.sql` created the table and nothing in the tree could put a row in it.

## A key is printed once, at issue, and nowhere else

The table stores `sha256(key)` and nothing else about the secret. `auth/keys.py:fingerprint` is
the one function that computes it, `PostgresKeys.verify` is the one lookup, and there is no verb —
no CLI, no operator door, no repair path — that reads a key back. `keys list` prints fingerprints.

So the moment a key exists in the clear is the return value of `Keys.issue`, and that value reaches
exactly one screen: the terminal that asked for it. Two callers ask.

- **`pinecall-runtime migrate up`**, on a database whose `default` org has no key. 0006 creates
  the org as its first row and this prints its key, which is the promise `CLAUDE.md` and
  `docs/decisions/routes.md` have both made since ms-2. A second `migrate up` finds a row and
  issues nothing: it says so and returns 0. Idempotence is the point — a verb a deploy runs on
  every push must not mint a key on every push.
- **`pinecall-runtime keys issue --org`**, over `POST /v1/ops/orgs/{org}/keys`. Its answer is the
  only response body in the whole runtime that carries a key.

Both print through `cli/keys/verbs.py:print_the_key`, and it puts **the key alone on the first
line**, with the org, the label and the warning under it. That shape is not decoration:
`infra/box/first_run.sh` reads it with `head -1`, and a format that mixed the key into a
sentence would need a parser on the box.

A key that is lost is not recovered; another is issued and the lost one revoked. That is cheaper
than any design in which a secret can be read back, and it is the only design in which a stolen
database is not a stolen tenant.

## Revoking is an UPDATE. It is never a DELETE

`revoked_at` is a timestamp on the row, and `_LOOKUP` filters on it — a revoked key stops verifying
on the very next request, with no cache to wait for and no process to restart.

The row itself stays because the **log** names it. An entry written by a key that no longer exists
is an entry whose author cannot be resolved, and a log that cannot say who wrote a line is not a
log. `keys list` shows revoked rows, marked `revoked`, for the same reason: the history is the
answer to "what happened", and deleting rows is how that answer stops being available.

Revoking twice is `false`, not an error and not a silent yes — the `WHERE revoked_at IS NULL` is
what tells the two apart, so `keys revoke` on a fingerprint nobody answers to is a `404` and never
reads as done.

## Three keys, three jobs, and none of them opens another's door

| key | who holds it | what it opens | where it comes from |
|---|---|---|---|
| `PINECALL_OPS_KEY` | the **box** | `/v1/ops/*` only | generated by `infra/box/setup.sh`, once, on the box |
| an org's API key (`PINECALL_API_KEY`) | a **worker**, a tenant's **app** | `/v1/routes`, the app socket, the log doors | `keys issue`, or the first one `migrate up` prints |
| `PINECALL_DEV_KEY` | a **laptop** | everything, with no database at all, as the default org | set by hand, in development, never on a box |

The ops key is the box's, not an org's, so every operator door names its org explicitly and the
key carries no `KeyRecord` — `api/_deps.py:an_operator` is a gate, not an identity. An API key
*is* the tenant: `KeyRecord.org` is the one field every door reads, and no door takes an org from
a parameter. A key that could ask for another org's routes would be a key that could route a call
into somebody else's agent, and a key that could name another org's log would read it —
`docs/decisions/orgs.md` says how the log knows whose it is.

`PINECALL_DEV_KEY` is the one that has to be argued for. It is not a weaker API key; it is a
different mode. Set it and `keys_for` returns a `MemoryKeys` holding it alone, *and*
`gateway/app.py:_a_pool` opens **no Postgres pool at all** — which is the whole point on a laptop
(a clone runs the gateway before a database exists) and a disaster on a box, where it would mean
the routes table and the api_keys table are both unreachable. So the box never sets it, and
`first_run.sh` issues the worker a real key instead. That is the decision the card asked for:
**the worker unit gets its own issued key, and a box's environment file never carries a dev key.**

The key is issued once and appended to `/etc/pinecall/pinecall.env`; a second deploy finds the line
and rewrites nothing, the same rule `setup.sh` follows for every secret it generates. An org's key
is therefore never the operator's laptop key, and revoking the box's key does not lock the operator
out of `/v1/ops`.

## What was deliberately not built

**Scopes on an API key.** `CLAUDE.md` says "hashed API keys with scopes" and the table has no such
column. Today every API key *is* the tenant: `auth/scopes.py:KEY_PROJECTION` is the constant
`tenant`, and the scopes in `types/token.py` are a **token's** — talk, chat, observe, supervise,
participate — minted per visit by the tenant's own server, not per key. A `scopes` column that no
door checked would be a permission that looks enforced and is not, which is worse than none, and a
table nobody reads is exactly what the hygiene rules delete. It lands in the milestone whose gateway
reads it.

**A `fleet` column beside `org`.** 0002 had both and every door read the fleet; 0006 keeps the org
and drops the other word. Two columns for one tenant was the twin the hygiene rules grep for.

**A key prefix that identifies its org.** `pk_` and 256 bits, nothing else: a key that carried its
org in the clear would leak the tenant's name into every log line that ever quoted a bad key.

**Any recovery path.** No "show me the key again", no reversible storage, no escrow.
